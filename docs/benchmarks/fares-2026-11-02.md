# National fares verification — 2 November 2026

Test host: Linux ARM64, Rust 1.99.1, Node 24.22.2, local `/mnt/ssd` storage. Production containers were separately built with Rust 1.94, Node 24 and Bun 1.3.6 and passed the Compose integration test. These are development-host measurements, not Raspberry Pi capacity claims. Raw measurements and query plans are in [fares-2026-11-02.json](fares-2026-11-02.json).

## Input and database

The live BODS archive was 2,372,579,710 bytes, SHA-256 `794e60367558402049039e3cd79106e60445f75601f1b787815b9c52ac5f7889`. Its 565 nested ZIPs and 240 direct XML members contained **154,278 NeTEx XML documents**, approximately 36.2 GB uncompressed. The importer stored **45,070,264 projected entities**, in addition to document ownership and network/zone links.

| Run | Wall time | Peak RSS | SQLite changes | Result |
| --- | ---: | ---: | ---: | --- |
| Initial national import | 74 min 33 s | 352 MiB | 90,828,329 | 154,278 documents and 45,070,264 entities inserted |
| Identical archive, final ARM build | 1.88 s | 18.5 MiB | **0** | All documents skipped; generation stayed unchanged |
| Controlled one-price update, final ARM build | 4.96 s | 200 MiB | **5** | One document and two fare entities updated; no entities inserted/deleted |

The controlled update changed the first `<Amount>` in `Nu-Venture_324/77_AD_SGL.xml` from `1.80` to `1.81`. All other uncompressed member contents were preserved. The two changed entities were the monetary price and its containing price group. The other 1,114 entities in that document were unchanged; all 565 nested ZIPs skipped parsing and scratch copies. The initial controlled run advanced generation to 2. After restoring the official input, the final accelerated runs repeated the same zero-write/update checks and restored the official input again, ending at generation 5. This demonstrates a controlled incremental case, not a measured real next-day feed; upstream XML filename/identifier churn can reduce savings.

The initial SQLite file was **69.8 GiB**. Peak WAL was **70.2 GiB**; the first load temporarily needed about **140 GiB for database plus WAL**, in addition to archives, scratch and free-space reserve. The controlled update's WAL before checkpoint was only **107,152 bytes**. Its OS block-output counter was 284 KiB, confirming that unchanged nested archives were not copied to scratch. The identical repeat left the database size unchanged and its WAL at zero.

The first import is expensive because it writes roughly 91 million indexed records atomically and finalizes/checkpoints a large WAL. Daily work depends on changed input. Storage retains original compressed XML and detailed JSON projections; the measured footprint is a deliberate cost of keeping conditions and references accessible rather than reducing fares to isolated monetary amounts.

The initial run used the parser optimization described below. Unchanged-input fast paths and ARM SHA acceleration were finalized afterward; the full fresh import was not repeated with the final accelerated build. Software-SHA repeat/update baselines were 6.23 s and 20.69 s; the final ARM build reduced these to 1.88 s and 4.96 s. Hashes remained compatible with the existing database and the 1,114 unchanged entities in the edited XML. SHA acceleration detects CPU support at runtime and retains the software fallback. Separate binary hashes and both measurement sets are recorded in the raw results. Other development checks ran intermittently during the initial measurement; timings should be treated as indicative for this host.

## API

Each scenario used 100 warm requests at five concurrent clients against the full fares database. The harness used a fresh API process, a small timetable fixture, authenticated HTTP requests and generation-aware worker caching. “Cold” means the first request to that scenario in this API process; OS disk caches were not explicitly cleared. A separate database scan was also running, so these are not isolated storage measurements.

| Scenario | First request | Warm p50 | Warm p95 |
| --- | ---: | ---: | ---: |
| Product page | 32.85 ms | 9.45 ms | 14.28 ms |
| Document price page | 9.87 ms | 4.07 ms | 6.27 ms |
| Single product | 3.27 ms | 1.46 ms | 3.25 ms |
| Operator product page | 7.15 ms | 4.72 ms | 6.54 ms |
| Operator late in the dataset | 8.19 ms | 4.62 ms | 6.10 ms |

Plans used `entities_category`, `entities_document_category` and `links_lookup`. Operator filtering used the document/category index plus a bounded result sort. Entity payloads are fetched individually after selecting a page of IDs, avoiding a page-sized allocation of potentially large zone JSON. Large JSON and original XML responses stream with backpressure.

## Parser optimization and checks

A real 6.7 MB Arriva matrix containing 12,118 projected entities took 0.707 s before caching frame currency defaults and 0.369 s afterward. Every entity identity/hash was identical between the two databases. The change removes repeated scans of large sibling collections while finding inherited defaults.

Verification covered:

- Rust importer tests for nested ZIPs, archive revision renames, unchanged archive hashing without scratch writes, exact decimals, namespaces/CDATA, duplicates, updates/deletions, stable IDs, empty/malformed inputs, disk-full rollback, killed writers, locking, snapshots, backups and physical no-op database/WAL behavior.
- Existing timetable tests and API schema/repository/worker/HTTP tests, plus fares filtering, cursor scope/generation, authentication, original XML, large Unicode streams, snapshot consistency, cache refresh and timetable agency/route/stop links.
- A live Rust download of the complete current BODS ZIP, followed by conditional reuse through the signed redirect returning 304.
- National SQLite `PRAGMA quick_check` returned `ok` after scanning the completed database (925 seconds). The imported document count and exact controlled monetary change were separately verified.
- Docker builds and isolated Compose tests for both import jobs, read-only API mounts, live fare changes, restart, no-op repeats and checked backups.

The API serves catalogue data and conditions. Journey fare selection still requires evaluating validity, passenger eligibility, zones, direction and purchase conditions.

## Reproduction

```sh
cargo build --release --locked --manifest-path apps/fares/Cargo.toml
python3 scripts/create-fares-price-change.py /mnt/ssd/bulk.zip /mnt/ssd/one-price-change.zip
python3 scripts/benchmark-fares.py --feed /mnt/ssd/bulk.zip \
  --feed /mnt/ssd/one-price-change.zip --output /mnt/ssd/new-fares-benchmark
node scripts/benchmark-fares-api.mjs --database /mnt/ssd/new-fares-benchmark/fares.sqlite \
  --output /mnt/ssd/new-fares-api-benchmark --samples 100
```

Build the API and the timetable debug importer before running the API harness. Output paths must be new. The synthetic archive is benchmark data; restore the original archive with a final import before reusing that database as an official-feed snapshot. The retained test database at `/mnt/ssd/buslane-fares/national-optimized/fares.sqlite` was restored to the original official archive after the measurements. For real daily-change measurements, pass two consecutive original BODS archives instead.

Run the optional live downloader test explicitly with SSD temporary storage:

```sh
TMPDIR=/mnt/ssd/buslane-tests cargo test --locked --manifest-path apps/fares/Cargo.toml \
  live_bods_download_and_conditional_redirect -- --ignored
```
